# Rain Next 增量审阅与资产处置 V2

## 0. 结论

推荐继续当前 React／Tailwind／Base UI 路线；不重建 Foundations，不按组件数量推导成熟度。Card 值得优先替换，但理由是现有样式配方与改造能力不足，不是它的代码短、使用原生元素，或缺少复杂 Headless 引擎。

本轮输出分为：**源码事实、机制实验、工程判断、实施建议、尚未验证。** 来源编号见 [07](07_来源索引与核对记录.md)。

## 1. 审阅范围与限制

- Rain 固定 Commit `321e1a0c1b5f9284e0fcb5167fa059d6174b1752`。
- 本轮增量阅读：Card、rainCn、Core UI 消费示例、Core UI 浏览器用例、Badge 源码；固定版本的其他基础与治理事实沿用前两轮已读取材料。
- 上游增量阅读：固定 Commit 的 Card 作者源码、Nova Card 样式段，以及当前官方 Card 文档。
- 本轮没有获取完整项目工作区、安装依赖、运行 TypeScript／Vitest／项目 Playwright，也没有运行实时 Figma 审阅。
- 确认 Core UI 页面存在两处 Card 用法；搜索服务返回不完整结果，因此不将“两处”表述为全仓调用总数。
- 已运行两个独立 HTML／CSS 机制实验，使用容器 Chromium 144.0.7559.96；不等于项目 Chromium 版本的回归验证。

## 2. 原建议应修正什么

### 2.1 “已有”不等于“必须保留”

Card、Badge、Surface、Link 均有源码，但上一轮合同索引已明确它们仍有早期配方、独立登记与验证欠项。[R15]

**建议：** Card 优先替换；其他三者保留并定向检查，不因同属早期组件就一并推翻。成熟度较高的 Button／Input／Select／Dropdown／Tabs 等继续作为接入对象。[R04]

### 2.2 Card 的部件骨架已经存在

现有七部件与上游基本相同；支持原生属性、children、className 和 ref；Title 有标题级别选择。说“完全不支持组合”与源码不符。[R17]

真正需要加强的是统一疏密、视觉规则的局部覆盖、插图／通栏内容、缺省部件组合与场景验证。这些改进不需要另造一个卡片状态引擎。

### 2.3 shadcn 的样式和语义也要评估

上游当前模板使用 div，Nova 样式默认裁切内容，Footer 带底色和边界；这些不自动优于 Rain 的 article、标题级别或更克制的 Footer。[U01][U02]

采用的是可组合实现与经验，不是把所有上游默认决定当成项目硬规则。

## 3. 增量发现

### F-01｜确定事实：配方零散，局部调整缺少统一入口

现有 `.rain-card__header` 使用 `18px 20px 14px` 留白和 `6px 18px` 间距；Content、Footer 又分别设置不同数值。旧样式使用早期语义别名，Card 本身没有尺寸轴和专用 Local Recipe。[R18]

影响：AI 调整整体密度时需要理解多处规则，容易只改到一块；但固定值本身不等于必然的视觉错误。

建议：统一 Card 的主要区域间距与内侧留白；仍允许 header 内标题—说明的细间距独立。不得把整个 Card 的所有间距强制绑成同一个值。

### F-02｜已复现机制：换成 rainCn 不能自动消除旧 CSS

Card 使用字符串拼接；rainCn 已在库中具备 Rain 工具类冲突处理。[R17][R19]

更重要的是：普通、未分层的旧 CSS 与工具类样式的优先级不是由 className 字符串顺序决定。独立实验中，`.rain-card__content` 的横向 20px 留白压过 `@layer utilities` 中的 0px 工具类；调换类名顺序无效；取消旧规则匹配后才变为 0px。[E04][X01]

**结论边界：** 这证明 CSS 机制与接入风险，未测量真实项目构建产物。Codex 必须验证项目实际层级和 computed style。

建议：Card 迁移时移除或局部迁移其旧视觉声明；不可仅追加 Tailwind 类，也不可把全库 styles.css 一次性包进新 layer。

### F-03｜确定事实：上游 slot 与 Rain slot 不相同

上游为 `card / card-header / card-title / card-action / card-content / card-footer`；Rain 为根 `data-rain-id=ui-card` 和 `root / header / title / action / content / footer`。[R17][U01]

如果只改属性而不改上游关联选择器，Action／Description／Footer 相关规则会错配。反之，直接换标记会影响既有测试与追踪。

建议：本批保留 Rain 标记，完整转译上游关联规则；禁止同一个 data-slot 填两个值来假装双重兼容。

### F-04｜已复现机制：后代选择器可能被嵌套 Card 误触发

上游 Nova 卡片包含后代 Footer 检测，作者 Header 模板也通过后代 Action／Description 检测改变布局。[U01][U02]

独立实验中，外 Card 没有自己的 Footer，内 Card 的 Footer 仍触发外层 `:has([data-slot=footer])`；改为直接子级条件后，外层不再受到影响。[X02]

**这不是“所有嵌套都必须用直接子级选择器”的结论。** 水平媒体组合可能有合法包装层；此时应使用明确的局部配方或只识别所属 Card 的规则，而不是扫描整个子树。

建议：测试嵌套 Card、嵌套控件中的同名 slot；不要为解决它引入递归 clone children 或整套注册系统。

### F-05｜确定事实：本批并不需要新 Headless 选型

本次审阅的上游 Card 作者文件直接使用 React 与 cn，不直接调用 Base UI／Radix 交互原语。[U01]

建议：替换 Card 不升级 Base UI、不引入动画引擎、不安装名为 `cn` 的新包；上游模板中的 cn 由实际项目工具函数替换为 rainCn。其他组件仍遵循当前 Base UI 相容策略。

### F-06｜确定事实：至少两处消费和已有断言需要迁移

Core UI 当前有标准课程资源 Card（带 Footer）和 `variant=raised` 的回顾 Card（含 Rain Button）；相关测试检查 article、标题级别、slot、两个 Card 的呈现，以及根不是按钮。[R20][R21][R22]

建议：保留有效语义与入口，允许有计划改变视觉。不要为了测试转绿删除“根不是按钮”等有效断言，也不要把旧截图覆盖成新结果继续当历史。

### F-07｜确定事实：当前 Card 尚无独立 Manifest／Registry

现有合同索引明确该缺口，公共源码存在不等于安装关系已闭合。[R15]

建议：本批补精确的 Card 元数据和本地源码登记；沿用当前格式。无需先把全库转换为标准在线 Registry，但不能冒称已有 CLI 安装服务。[R12][E07]

### F-08｜迁移风险：图像裁切与焦点保护要分开

当前 Rain 根 `overflow:hidden`；上游 Nova 也有裁切，不是换源就会自动解决。[R18][U02]

建议：普通 Card 优先保留可见溢出；媒体通过局部裁切容器处理。触发器贴边、角标、Portal 内容、长标题等须在真实组合中检查。这个默认是本计划提案，不是已接受视觉。

### F-09｜确定事实：当前 FormItem／Select 仍有集成边界

FormItem 以 Context 提供字段关联，不向任意孩子注入完整属性；Select 未提供原生表单提交／约束校验桥接。[R08][R09]

建议：新 Textarea 要显式桥接；BM-B 先用宿主拥有草稿与校验的方案。此问题与 Card 替换分开，不顺手重写整个 Form。

### F-10｜架构欠项：组件展示较深，布局与业务验证仍不足

同一参考 Commit 中公共 Layout 仍为空占位，四项 BM 为未开始；现有局部 Recipes 不代替四项完整业务验证。[R02][R10]

建议：Card 只完成最小接入和四个组合示例，随后进入 Layout、BM-A／B；不要转成“全量卡片设计专项”。

### F-11｜正确机制但不可夸大：Local Recipe 不是运行时沙箱

现有定义函数验证记录字段和部分格式；普通 CSS 继承、选择器范围及传入对象仍需测试与治理。[R16][R19]

建议：通过同屏目标／非目标、嵌套和连续改造验证隔离；不把“有 recipe 类型”描述为自动禁止所有越界样式。

### F-12｜原有问题：视觉接受不等于颜色全部合规

现有颜色清单仍保留弱文字、边界、Focus 等问题，计数为配对数，不是独立缺陷总数。[R11]

建议：不扩大已有例外，不将问题配方无判断复制给新 Card。新标题／说明用真实背景验证；不以新组件任务名义擅自重定义品牌色或关闭旧欠项。

## 4. 资产处置建议

| 资产 | 当前动作 | 理由 |
| --- | --- | --- |
| Foundations／图标 | 保留，补最低必要映射 | 已有基础与来源，重复建设会造成双重事实 |
| Button／Input／Select／Dropdown／Popover／Tabs | 保留、补接入缝隙 | 已有真实能力与局部视觉接受，不宜批量换源 |
| Checkbox／Radio／选择卡／Tag 家族 | 保留，按使用完善 | 原生实现与复合资产不需要为 Card 更换 |
| Card | 优先 `adapt-shadcn` 替换候选 | 配方和可修改性薄弱、源码与语义迁移成本有边界 |
| Badge／Surface／Link | 独立检查，默认保留 | 不因 Card 薄弱就认定同批资产都应替换 |
| Layout／Table／任务容器等缺口 | 按 BM 任务链补齐 | 决定什么时候能够使用新库搭真实页面 |

Card 不承担选择、整卡导航、业务请求、任意模态任务和全局布局；这些能力从相应组件、布局或业务宿主组合。

## 5. 审阅结论的置信边界

确定：固定版本文件、函数与样式声明、明确的已登记范围。

机制已实测：两个独立 CSS 实验，结果见证据目录。

待本地验证：所有调用与间接导出、真实 CSS 构建、治理脚本是否拦截新路径、全部主题与设备、实际改造效率、工作区是否有未提交新版本。

未得出的结论：Card 比上游慢多少百分比、替换必定耗时几小时、全库 64 项已达到同等成熟度、项目已通过本轮测试。
