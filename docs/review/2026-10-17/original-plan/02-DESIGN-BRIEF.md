# 雨课堂原型设计要求｜v1.2
## 用于设计消费，不是另一套全局 Token

本文件整理用户在本次对话中的明确偏好，并给出落实方法。偏好与实施建议分别说明。应将适用内容合并进现有设计入口；不要连同全部历史记录在每次任务中重复加载。

## 1. 用户明确要求

目标：视觉高保真、成熟产品感、适合真实业务，不是“套雨课堂 Token 的线框原型”。允许 AI 创造页面私有组合；局部调整不能污染公共组件。

优先顺序：工作台／复杂操作页 → 数据展示／报告页 → 卡片内容页 → 表单页 → 表格／列表页。题型、难度 Tag 的例子用于解释信息表达，不意味着本轮首先补标签或主要优化表格。

默认流程：先交两个或多个有明显差异的布局方向，用户选择后细化。明确“快速出图”时自行比较、选一版、完成交付。必须保持相同业务范围，不能靠删去关键功能制造方案差异。

常规尺寸为主；复杂、拥挤、窄区域并不自动授权选最小或 compact 控件。局部更密集需要任务理由，与相邻控件保持协调。控制尺寸时使用现有合法 API，不通过零散高度覆盖破坏行为。

普通业务页面通常以 16px 为最大标题字号。重点数据常用 18—20px；少数特殊情况 22—24px。不把数字当作所有场景的永恒上限：投屏、大屏及另有明确要求的页面独立处理。此偏好先用于本轮页面选择，不直接改所有公共组件默认值；发现共享默认冲突时集中提出修订。

弱信息应真的退后；页面要有充分的分组留白、疏密对比、整体秩序。用户愿意比较更淡辅助信息，但这不等于新资产可以声称低对比度已达标，也不覆盖必要操作与错误提示的可读性。

## 2. 设计步骤：先关系，再组件，再细节

### 第一步：业务信息分组

写明主要任务、操作对象、阅读对象、全局范围、局部条件、辅助内容及必要状态。关键业务资料已在上下文时应利用，不能让设计师重新讲一遍；缺少会改变设计的事实时只问该项。

同一对象的数据与动作优先相邻；同一范围的筛选成组。不要把 AB 卷、分组筛选、评分输入、辅助解释放成同一层级。

### 第二步：整页主次

先决定视觉主要聚焦的任务区域，再安排支撑信息。不规定每个模块都必须有一级、二级、三级各自强烈的样式。辅助模块可以只有一个平静的标题和内容。

不要默认所有区域套 Card、标题加粗加大、每块加分隔线或数字强调。必要状态可更突出，但不是所有提示都红／蓝高亮。

### 第三步：模块内部精细版式

一个模块可以同时包含横排、纵排、跨列与局部网格。按内容长度和相互关系安排：长字段跨列、短字段并排、说明跟随被解释对象、操作靠近对应结果。

秩序来自稳定的信息位置、成组关系、阅读路径、光学对齐与节奏，不是强迫所有元素坐标相同。先调整组间留白和比例，再考虑缩小组件。

### 第四步：把信息翻译成合适的视觉

| 信息任务 | 可比较的表达方式 | 避免 |
| --- | --- | --- |
| 题干、长作答、正文 | 阅读区域、清楚分段、适合内容宽度的预览 | 为了齐行把所有内容截成一行 |
| 题型等类别 | 现有标签、图标与文字，或在高密度场景保留文字 | 每个类别强行一种高饱和色；新增无意义色彩 |
| 难度等有序等级 | 既有等级标签或轻量有序编码；保留文字含义 | 把有序数据当随机颜色分类 |
| 状态、进度 | 状态文字与适用的点／徽标／进度条组合 | 只靠颜色区分；把“待处理”做成执行按钮 |
| 时间、来源等辅助元信息 | 位置固定的弱文字和节制图标 | 与任务标题同重、每项都包装成 Badge |
| 报告趋势／比较／构成 | 分别评估线、条、构成图、紧凑表或文字结论 | 全部写成纯文字；或为显得丰富乱加图表 |
| 数值与单位 | 重点数值按 Data 角色，单位与说明保持 UI 字体 | 所有数字都超大；中文单位继承特殊数据字体 |

这张表是设计判断提示，不是“每个类型必须一种组件”的硬规则。丰富来自有意义的表达差异，不来自标签、图标或颜色数量。

### 第五步：按操作选控件

同级内容区域可考虑 Tabs；改变少量互斥条件可考虑 RadioGroup／标签筛选；更多值再考虑 Select；动作使用 Button／文字按钮／IconButton；复杂独立字段进入合适表单容器，而不是塞进单个菜单项。

不要因外观像按钮就丢失单选语义。可以创建页面私有的分段外观与复合区域，但尽量复用已有状态、焦点、键盘、浮层行为。

### 第六步：浏览器中检查设计

先整页，再区域，再组件，再状态。真实看效果，不能只保存截图、检查无溢出就宣称高保真完成。

检查最明显的三处视觉焦点是否都必要；高频操作是否顺手；辅助内容是否退后；组间空白是否可辨；密度和字号是否突然跳变；长内容、空值、加载和失败是否破坏原版式。

使用用户实际桌面容器，再看窄容器与放大后的可用性。容器宽度与端口以当前场景为准，不把历史 1200、390 或 5326 全部写成系统永恒默认。

## 3. 创造与保护范围

- 自主：页面排布、区域内混合排版、已有尺寸与变体选择、文字／图标组合、页面私有组件、Mock 数据和状态。
- 需要共享评估：新增公共变体、改共享默认、引入未批准依赖、同一需求多次复现后升级公共组合。
- 不直接做：修改公共组件只为一页、删除必要无障碍行为、绕过 Token 随意造品牌样式、复制底层交互控制器。

复用基础行为不等于必须照抄固定外形。新的业务组合先留在当前原型；经重复验证再沉淀，不一开始为每个区域设计稳定的公共 API。

## 4. 三种来源如何使用

用户 Figma：本轮设计质量校准来源，不是要求之后每页都必须提供设计稿；根据业务保持信息关系，而不是逐像素抄旧数值。静态画面不能证明交互、状态和可访问性通过。

现有雨课堂资产：已确认品牌和基础行为的优先依据。上次实验页尚未获接受的部分不能冒充优秀视觉模板。

成熟外部组件与示例：提供成熟结构、交互和表现手法；适配雨课堂风格，不把其他品牌的字体、颜色和默认视觉整套带入。

## 5. 对比度与“退后”的处理

先用更轻字重、稳定位置、适量缩减信息、弱底色与留白降低视觉重量。具有信息意义的辅助文字不自动豁免对比度要求；纯装饰、禁用和必要交互分别判断。

用户明确要求比较更淡实验方案时可以呈现并如实说明未达标项，但不得把方案展示等于标准通过，不得把必要按钮或错误信息淡到不可辨。不要以合规为理由把所有元素统一加深，也不要用“辅助”当作放弃可读性的总开关。

## 6. 反馈沉淀，避免下次重犯

每次只提取少量可迁移的决定：触发条件 → 原问题 → 新设计判断 → 适用范围 → 证据／确认状态。布局关系进入组合指南；公共缺陷回共享能力；单页像素和文案留在局部。

第一次可运行、自查后、用户反馈后分别留痕。要求解释的是关键设计取舍与实际读取／检查，不是模型隐藏思维链。

这份文档本身不是已安装 Skill，也不证明 AI 已读到。接入时验证真实加载和工具调用，并用新任务检查是否起效。

## 7. 本轮 Token 准备如何支撑设计

F03调整的是“新原型优先推荐”，不是全库清除大字号或微尺寸。一般标题从16/24、常规正文从现有14/22方案起步；重点数据常用18/20，特殊需要到22/24，具体行高与字形需在当前资产中核对。以上不限制浏览器放大、用户阅读设置或独立大屏需求。
常规尺寸搭配先在工具栏真实组合中比较；允许静态Tag与输入框高度不同，不允许无理由混入极小操作。不要通过改公共Density的一处数值期待所有组件自动协调。
48/64等大间距只有真实分组需要才用，留白关系不是硬公式；不用强行给每个模块三级层级。轻阴影用于合适对象，不让Card全局加重。
配色默认从已检查的完整组合选择；已有分类标签/难度色优先，未知图表新色不自行写入全局。未决对比度说明与高保真评价独立。
构建产物里真实查看首稿：各区域是否在服务同一主任务？辅助信息是否安静？颜色/尺寸样式是否真正生成？视觉指导被读取与执行要有可见工作记录，而非自述。
