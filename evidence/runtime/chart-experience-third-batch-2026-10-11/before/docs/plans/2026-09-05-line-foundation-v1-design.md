## 1. 建设目标与职责

目标是让 AI 能够先找到合适的组件或配方，再使用少量公共材料进行局部组合；重复用途具有稳定默认，局部修改不会意外改变其他消费者。

“线条”是知识检索主题，不新增一层与 UI、Layout、Pattern 并列的架构，也不把研究中的全部线条用途展开成 Token 树。

| 内容 | 放在哪里 | V1 如何处理 |
| --- | --- | --- |
| 可复用的固定粗细 | Foundations 的公共 Line Thickness | 新增 1–6 CSS px，待实施 |
| 颜色、圆角、间距、Focus | 各自既有 Foundation | 复用；不复制一套 Line Color、Line Radius 或 Line Focus |
| 实线、虚线 | 绘制样式选项，以及组件／配方规则 | 支持基础选择；不为每个枚举新增全局 Token |
| 用哪档粗细、哪种颜色、长度、位置、状态 | 对应组件或配方 | 同类用途复用默认，按已开放边界修改 |
| 路径、箭头、端点符号、分叉、线上标识 | 对应图形部件或绘制能力 | 先保留职责归属，真实需求出现后再抽取公共能力 |
| 数据到粗细、方向、几何的映射 | 对应图形能力与业务／领域适配 | 不塞进固定粗细档位，不预建通用映射系统 |

公共能力的范围可以大于公共 Token。公共部件、配方和绘制工具是否建设，仍取决于消费者及需求是否稳定。

## 2. 公共粗细合同：采用 1–6 CSS px

### 2.1 身份与值

公共名称采用 **Line Thickness**，中文为“线条粗细”。避免用文字行高 `line-height`，也不把概念限制为 Border 或 SVG Stroke。

| Token 身份 | CSS 变量 | 值 |
| --- | --- | --- |
| `Line/Thickness/1` | `--rain-line-thickness-1` | `1px` |
| `Line/Thickness/2` | `--rain-line-thickness-2` | `2px` |
| `Line/Thickness/3` | `--rain-line-thickness-3` | `3px` |
| `Line/Thickness/4` | `--rain-line-thickness-4` | `4px` |
| `Line/Thickness/5` | `--rain-line-thickness-5` | `5px` |
| `Line/Thickness/6` | `--rain-line-thickness-6` | `6px` |

代码合同名为 `lineThicknessTokens`，键为字符串 `"1"` 至 `"6"`，值为上表的带单位字符串；类型名为 `LineThicknessTokenName`。这些名称目前均未实现。

- 这是可直接消费的公共尺寸规格，不要求再绕经全局 Semantic 别名。
- 数字表示 CSS px 数值，不表示强调等级或状态。`3` 不自动等于“选中”，`4` 不自动等于“标题”。
- 1–6 是首版选择集，不是所有线条的合法上限，也不要求每个组件开放六档选择。
- 这些属于公共尺寸 Token，独立于原 Spike 的 Semantic Color 数量统计。

### 2.2 单位、密度与稳定性

采用 CSS px，避免粗细跟随根字号变化。Compact / Default、文字字号和主题默认不改变这些数值；组件如有经确认的差异，应改变自身引用。

CSS px 不等于设备物理像素。浏览器缩放、设备像素比、变换和 SVG 坐标系仍影响最终栅格化；本合同不承诺所有环境都呈现相同的物理像素边缘。

数值身份保持稳定：不能把 `Line/Thickness/3` 改成 `4px`。未来需要 `0.5px` 或 `8px` 时，在真实需求审查后新增身份，不插级重排已有名称。局部特殊尺寸先按既有 Local Candidate 规则处理。

V1 不新增 `0` 档。“不显示线”“隐藏但保留位置”“取消边框占位”是不同布局或状态行为，由消费者明确处理，不能统一用粗细为零替代。

## 3. 绘制方式与基础线型

### 3.1 同一粗细可以有不同落点

| 表达 | 粗细应用位置 | 仍由消费者决定 |
| --- | --- | --- |
| 容器边框 | `border-width`，每一边的厚度 | 边框颜色、样式、容器圆角、盒模型 |
| 横向填充条 | `height` | 长度、定位、背景颜色、是否圆头 |
| 竖向填充条 | `width` | 长度、对齐、背景颜色、是否圆头 |
| SVG 路径 | 适合时使用 `stroke-width` | 路径坐标、缩放、端点、拐角、箭头；不在首批桥接范围 |

横条和竖条的另一个尺寸表示长度，不能因为数值碰巧相等，就改用粗细 Token 管理长度。条形也需防止布局压缩，保证最后的实际粗细符合所选值。

数据驱动的宽线、带状几何可以使用独立计算结果。描边或填充、等宽或变宽，都不是判断其必须使用公共档位的依据。

### 3.2 实线与虚线

普通 UI 的基础样式选择先覆盖 `solid`、`dashed`。点线 `dotted` 暂缓；全局虚线段长、间隔、端点节奏暂不建设。

对使用 CSS Border 的消费者，复用原生 `border-style`；同类用途的默认样式由配方固定，不给所有虚线赋予统一业务含义。原生虚线的段长与间隔不由该属性精确控制，因此首版接受浏览器渲染差异。[CSS 边框规范](https://www.w3.org/TR/css-backgrounds-3/#border-style)

填充条加上 `border-dashed` 不会把背景填充变成虚线。需要虚线时，消费者应选择适合的边框或精确绘制方式；不承诺所有使用粗细 Token 的部件都支持相同的线型 API。

精确 dash/gap、路径转角、箭头尺寸与动画时序，随具体图形消费者设计。基础内容分隔线不开放独立端点参数；容器圆角继续由容器管理。

## 4. Tailwind 消费方案

### 4.1 首版只开放三类固定入口

复用现有 [Tailwind bridge](../../packages/foundations/src/tailwind-theme.css)，以静态 `@utility` 声明以下入口。Tailwind 官方支持通过该方式登记自定义 utility；这里仅采用其扩展机制，合法数值和用途仍由 Rain 决定。[Tailwind 自定义样式](https://tailwindcss.com/docs/adding-custom-styles#adding-custom-utilities)

| 入口，`n` 取 1–6 | 只设置的属性 | 典型用途 |
| --- | --- | --- |
| `border-rain-line-n` | `border-width: var(--rain-line-thickness-n)` | 整体边框厚度 |
| `h-rain-line-n` | `height: var(--rain-line-thickness-n)` | 横向填充条粗细 |
| `w-rain-line-n` | `width: var(--rain-line-thickness-n)` | 竖向填充条粗细 |

共 18 个明确入口，三种表达共用六个事实值，不是 18 个新的 Token。表中的 `n` 是文档简写；实际实现与消费必须是完整静态类名，不允许运行时拼接 `h-rain-line-${n}`。

以下是桥接设计示意，当前代码中不存在：

```css
@utility border-rain-line-3 {
  border-width: var(--rain-line-thickness-3);
}
@utility h-rain-line-3 {
  height: var(--rain-line-thickness-3);
}
@utility w-rain-line-3 {
  width: var(--rain-line-thickness-3);
}
```

颜色和样式独立组合：用途合适的颜色，在边框上应用到 `border-color`，在填充条上应用到 `background-color`；绘制属性不改变颜色的用途归属。边框另配 `border-solid`／`border-dashed`；圆头填充条按其配方复用既有 `rounded-rain-full`。

### 4.2 保持消费边界

- 不把 Line Thickness 挂进 `--spacing-*`，不为获得 1px 横条而新增公共 Spacing 1。现有 [Spacing 合同](../../packages/foundations/src/composition-contract.ts)保持独立。
- 不随之开放 `p-rain-line-*`、`gap-rain-line-*`、`m-rain-line-*`、`size-rain-line-*` 或 min/max 尺寸入口，也不允许通过其他任意值写法借用粗细做这些事情。
- 首版 `border-rain-line-*` 设置整圈边框厚度，不隐含上下左右、逻辑方向或 `divide-*` 的全部家族。实际出现单侧边框消费者时，再明确其最小入口与冲突规则。
- 首版不新增通用 outline/ring、文字下划线、SVG stroke 或箭头入口。Focus 保持现有完整合同；图标保持来源几何。
- 正常 CSS 可以在已登记的共享实现或 CSS 例外中引用公共变量；这不等于对页面开放随意的内联样式和任意视觉值。
- 状态类和响应式类必须与消费者的已登记规则对应；Tailwind 能生成某个组合，不表示 Rain 默认批准该组合。

### 4.3 新能力必须经过实际消费链

实施时必须一起核对：公共值 → CSS 变量 → bridge → 源码扫描 → 类名合并 → 配方消费 → 浏览器渲染。

当前 B2 有精确的顶层 utility 清单与保护路径；新增类不是改完 CSS 就已接通。至少需要：

1. 登记 18 个入口及 `border-dashed` 的合法消费范围，保持 Rain 命名空间和精确白名单。
2. 核对线条试点目录已被明确的 `@source` 覆盖，并登记对应检查路径。现有 Playground 的 `@source "./"` 已覆盖其下源码；仅在现有范围外时新增 source。继续使用 `source(none)`，不扩成全仓库扫描。
3. 更新 [rainCn 合并规则](../../packages/ui/src/utils/rain-class-names.ts)：同一状态下的粗细入口要正确替换同属性尺寸；边框颜色、粗细和线型不能相互误删。
4. 更新 [B2 验证器](../../scripts/verify-tailwind-b2.mjs)与对应合同；校验真实存在的类和值，而非仅接受 `rain-` 前缀。

新检查点可以复用既有工具，但应独立登记线条的验证范围；原 B2 的 Button/Input/搜索操作区对照基线保留。旧验证通过不能充当新线条能力的证据。

## 5. 组件默认、配方与别名

公共 Token 回答“有哪些粗细可选”；配方回答“此处为什么用这一档、出现在哪个部位、什么时候变化”。

| 情形 | 推荐做法 |
| --- | --- |
| 新组件需要一条固定线 | 在自身 Part 的配方中直接选择公共粗细，不强制增加一层别名 |
| 该部位需要稳定的独立调整入口 | 由组件拥有必要别名，映射到公共粗细；不复制新的数值体系 |
| 两个部件恰好都用 3px | 分别持有自己的选择，不自动合并成共同变化的配方 |
| 只把某个 Tab 的指示条从 3px 改为 4px | 改该 Tab 的引用；不改公共 `3`，不改标题标记 |
| 页面需要局部差异 | 先用已有 Variant，再按开放 Part 使用 Local Recipe；结构或行为变化需要时才 Fork |
| 合法公共值不足 | 登记 feature 范围的 Local Candidate，保留原因与消费者；不自动晋升全局 |

现有 Button、Input 等组件拥有自己的边框与 Focus Token。首版采用增量建设，不为了数值同为 1px 而自动迁移这些引用；后续迁移须有组件自身的变更依据和回归范围。

标题标记与 Tab 指示条分别拥有默认行为。圆头标题标记优先复用 Radius；长度、间距、对齐和 Tab 的定位、选中、动画仍属于对应配方。此处不确认具体数值，也不新增公共 Marker 组件。

颜色遵循[最新颜色治理设计](2026-09-05-color-token-governance-design.md)：未来 Public Category 可直接消费，Semantic 可作为稳定别名。该颜色改造尚未实现；线条首版先用当前合法公共颜色，建设公共粗细不等待颜色迁移，也不预先开放未来色表。

## 6. 首批建设范围与一个真实消费者

### 6.1 已确认交付范围

| 产物 | 首版内容 | 交付身份 |
| --- | --- | --- |
| 公共粗细 | §2 的六个值、类型与公共 CSS 变量 | Foundations，实施后按实际审核状态登记 |
| 消费桥接 | §4 的 18 个入口；Border 的基础线型选择 | 现有 bridge 的受控增量 |
| 基础对照 | 六档边框／横条／竖条；实线与原生虚线边框 | 验证小样，不登记为 UI 组件 |
| 内容分隔试点 | 有标题的两个内容区域之间，一条轻量横向分隔线 | `local-experiment`，一个具名 Local Recipe |
| AI 使用入口 | 公共规格、用途边界、试点配方与修改示例 | 关联到实际文件，标明可用状态 |

首版没有完整 Divider、Title Marker、Tabs 公共组件的交付承诺。原生虚线在边框对照中验证；下述填充式分隔配方不因此开放虚线选项。

### 6.2 内容分隔试点配方

以下规则随 D3 确认为首批内容分隔试点的设计，不扩展为全库分隔线默认。

| 项目 | 试点规则 |
| --- | --- |
| 使用场景 | 两个已由标题和结构表达关系的内容区域之间，辅助视觉分组 |
| 粗细 | `Line/Thickness/1` |
| 绘制方式 | 横向实心填充条；平直端点 |
| 颜色 | 当前 `border-subtle`，以 `bg-rain-border-subtle` 应用到填充条 |
| 长度与对齐 | 跟随所属内容区域宽度，两端与内容边缘对齐 |
| 前后距离 | 由所在配方的布局与既有 Spacing 负责，分隔条自身不附带固定外边距 |
| 布局保护 | 避免被 Flex 压薄；只影响本区域，不改变其他消费者 |
| 状态 | 无交互，不增加 Hover、Selected、Disabled 或键盘焦点状态 |
| 可调整范围 | 本地配方可改粗细引用、选择适用的合法结构色、调整所属布局；不同用途不能直接继承全部默认 |
| 无障碍 | 此试点为冗余装饰，`aria-hidden="true"`；区域关系由真实标题和结构表达 |

以下仅示意实现后的静态消费方式，不能当作当前已可运行的代码：

```tsx
<div
  aria-hidden="true"
  data-rain-id="line-v1-content-divider"
  data-slot="divider"
  className="h-rain-line-1 w-full flex-none bg-rain-border-subtle"
/>
```

如果一条分隔线本身承担文档主题转换，应根据语义选择 `<hr>`；如果它能拖动调整区域大小，则属于可交互分隔器，需独立键盘、焦点和尺寸调整合同。二者均不能直接用本试点的装饰身份代替。

`border-subtle` 的试点选择不证明其适合必需的控件边界、状态提示或所有底色。其他用途应依据实际背景和非颜色线索验证可识别性；公共 Token 的存在不能替代用途审查。

## 7. 面向 AI 的最小使用知识

### 7.1 每次消费的顺序

1. 先判断线在表达什么：结构分隔、组件状态、强调标记、关系路径，还是数据量。
2. 按既有 `Template → Block → Pattern → Layout → UI → Primitive` 顺序寻找语义匹配的资产；Foundations 支撑所有层，不进入页面资产检索链。
3. 有合适组件或配方时，沿用其默认及开放的修改范围；不逐次重新拼粗细、颜色、状态。
4. 没有匹配资产且确需新表达时，选择公共材料与适合的绘制方式，记录本地用途和作用域。
5. 根据真正的职责处理特殊情况：Focus 找 Focus，标题标记找标题配方，Tab 找 Tabs，数据路径找对应图形能力。
6. 检查实际渲染、语义和局部修改范围，不把“类名合法”当成“设计正确”。

### 7.2 放入既有资产合同，不另建线条知识平台

未来实施时，复用现有 Manifest 与 Local Recipe 字段，按资产类型登记：

- 用途与反例：`useWhen`、`doNotUseWhen`、`antiPatterns`。
- 所有权与结构：`anatomy`、`parts`、`tokens`、`layoutConstraints`。
- 默认与变化：`variants`、`states`、`compositionRules`、允许与禁止修改项。
- 来源与可用性：真实文件、版本、`maturity`、相关配方及 Figma 映射状态。

试点 Local Recipe 保留既有 `id / scope / origin / classes / modifiedParts / candidateTokens / promotionStatus` 字段与 `local-experiment` 身份。`origin` 指向实际存在的试点资产或源文件，不虚构一个尚不存在的公共 Divider。

复用 [Local Recipe 工具](../../packages/ui/src/recipes/local-recipe.ts)不等于自动获得 CSS 隔离：实现仍需真实 feature root、局部选择器或实例范围及隔离验证。全局 Token 定义对页面任务保持只读；局部变化调整引用，不覆盖公共数值。

公共文档与检索入口必须区分“设计建议”“实际可用”“待审核”；实施前不能将本文中的 Token、类名或组件示意登记为可安装资产。常规消费文档保持简短，复杂图形知识按需链接，不要求 AI 每次读取完整研究。

### 7.3 必须覆盖的修改示例

| 用户意图 | AI 应采取的动作 | 应避免 |
| --- | --- | --- |
| 当前区域分隔线改厚一点 | 只改变本地配方的粗细引用 | 改公共 1px 的值、借用 Button 边框 Token |
| 标题旁放圆头竖条 | 查标题配方；适合时复用粗细与 `full` 圆角 | 先建设通用箭头／端点系统，或自定全库标题默认 |
| Tab 指示条变长 | 按 Tabs 的长度与定位规则修改 | 把粗细 Token 当长度，破坏选中／焦点行为 |
| 虚线框需要更精确的节奏 | 明确具体消费者的精度要求，再选择绘制方案 | 假定 CSS dashed 能指定段长，新增全局 dash scale |
| 拓扑线宽表示数据量 | 保留数据映射和图例，由图形能力实现 | 强制压到 1–6 档，或只凭外观猜测映射意义 |

### 9.2 后续实现必须取得的证据

| --- | --- |
| 数值与导出 | 六项身份唯一、值为 1–6px；类型／CSS 一致；公共导出可用且无私有值泄漏 |
| Tailwind 输出 | 18 个完整入口按各自属性生效；不会生成线条专用 padding/gap/margin 等未开放类；非法数字、任意值、动态拼接有拒绝证据 |
| 类名合并 | 同状态同属性的粗细正确替换；颜色与线型保留；h/w 相互独立；不同状态的类不被误合并 |

| 局部组合 | 试点内一条分隔线改用另一档，同页对照与第二个作用域保持原值；没有覆盖全局 Token 或修改其他 Master |

| 既有回归 | 完成本批必要的专项检查，再运行既有 `pnpm verify:tailwind-b2` 与 `pnpm verify`；旧组件与原 B2 基线的变化均有明确依据 |

## 10. 确认记录与延期事项

### 10.1 已确认的三项决定

| 编号 | 已确认决定 | 理由与代价 |
| --- | --- | --- |
| D1 | 采用 `Line/Thickness/1…6`，值为固定 CSS px；不随密度／字号变值 | 与用户提出的连续粗细范围一致，易读且可扩展；六档不保证每档当前都有真实消费者 |
| D2 | 采用 border/h/w 三类静态 Tailwind 入口，共 18 个；不并入 Spacing | 覆盖描边与填充条，消费属性明确；需同步 bridge、合并与校验，暂不覆盖所有边与绘图属性 |
| D3 | 增量建设公共规格与桥接；用一个 1px 轻量内容分隔配方加基础对照验证 | 可以验证组合方式且无需迁移旧组件；不代表 Divider、标题标记、Tabs 已完成公共 API 设计 |

确认日期：2026-09-05。决策来源：用户在本版交付并明确提示审阅三项建议后回复“确定”。D1–D3 现作为首版实施设计依据；§10.2 的延期事项保持延期。此次确认不表示运行实现或线条 V1 Human Gate 已完成，启动运行实现仍以用户后续的实施指令为准。

### 10.2 延期，不阻塞 V1

| 事项 | 再进入建设的触发条件 |
| --- | --- |
| 更多或小数粗细、点线、单侧边框入口 | 真实消费者在当前规格中表达不足 |
| 精确虚线、端点和路径拐角 | 明确的精度、品牌或图形一致性要求 |
| 标题标记与 Tab 的完整配方 | 对应组件进入建设，长度、状态和布局需求明确 |
| 独立公共 Marker、箭头、路径部件 | 多个真实消费者证明值得共享；不以外观相似直接抽取 |
| 图表、拓扑、带状几何与数据映射 | 对应业务场景、数据含义和交互目标明确 |
| 全库边框／Focus／下划线迁移 | 逐组件获得迁移依据与回归范围 |
| Figma 绑定与正式资产 | 实际设计工具接入与相应阶段启动 |
